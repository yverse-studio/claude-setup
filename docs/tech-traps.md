# Tech traps

Short facts that cost a thread a round once. One line each: the trap, the fix, the home of the detail.

- **Pushed migration:** never rename or edit one; add a new one. The rule and the exception live in [`publish`](../.claude/skills/publish/SKILL.md) (migrations), nowhere else.
- **Metricool drafts, UNVERIFIED LEAD** (Social app, 2026-10-26): the `draft` field exists in the connector schema; Social reports that `createScheduledPost` with `draft: true`, called from the Worker through an OAuth MCP client, cancels without a paid plan. Not re-tested here: test on the account before relying on it. Other Metricool limits: [`social-team/learnings.md`](../.claude/skills/social-team/learnings.md).
- **Playwright in a cloud thread:** launch with `executablePath: '/opt/pw-browsers/chromium'`; that Chromium has no H.264, so test video as WebM.
- **Cloud project chat gets its setup script only on a restart** (routing test 2026-10-27): a new project's chat container skips the environment's Setup script, even with Claude Setup picked (no `~/.claude/claude-setup`, no `settings.json`); threads get it. Restarting the project runs it, and the chat then has its hooks (yskills, 2026-10-27), so a new project's last setup step is a restart. Every container reports `CLAUDE_CODE_REMOTE_ENVIRONMENT_TYPE=cloud_default`, so that variable proves nothing. Auto mode denies the chat installing hooks into its own `~/.claude`, even when yskills asks ([Self-Modification], 2026-10-27), and that is not worked around: until the restart the chat gets persona and rules from the [boot text](../.claude/skills/operator/templates/project-instructions.md), and threads enforce routing on their own start (rule-guard `briefCheck`). Before guessing how a cloud environment behaves, read the platform's own docs (`read_documentation`, code.claude.com cloud environments) and check the container (`ls ~/.claude`).
- **Cloud environment cache:** the Setup script runs only when the cache is built (script text change, network change, about 7 days); [`cloud/bootstrap.sh`](../cloud/bootstrap.sh) has the detail. The guards update themselves from `main` at each session start.
