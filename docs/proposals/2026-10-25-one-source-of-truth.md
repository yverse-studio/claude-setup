Root cause: three of the five places hold rules, and only one of them is reviewed (the repo). The
other two are written by hand per session, so they drift and win by being loaded first.

What a session loads by itself (Anthropic docs, read 2026-10-25, `docs/research/2026-10-25-memory-and-source-of-truth.md`):
a cloud project thread gets each attached repo's root `CLAUDE.md` and `.claude/rules/`, the project
instructions (up to 16,000 characters) and the project memory's `MEMORY.md`; it does not load repo
skills, agents or subfolder `CLAUDE.md` files (they are read by path, `docs/MAP.md` Expertise). Local
auto-memory is machine-local and never reaches the cloud; project memory never reaches the laptop.
`CLAUDE.md` should stay under 200 lines; contradicting instructions make Claude "pick one arbitrarily".
So the repo's `CLAUDE.md` plus `docs/MAP.md` is the only layer every surface can share, which is why
the design puts rules there and nothing but pointers and state anywhere else.

## 2. The design

Four layers, each with one job. A fact lives in exactly one layer.

| Layer | What | Where | Who writes | Loaded |
|---|---|---|---|---|
| **Rules and lessons** (lasting) | every rule, every lesson, every how-to | claude-setup, one home each, indexed by `docs/MAP.md` (new top section "Start here" and a "Lessons" row listing every lessons home); product-specific lessons in `<product repo>/docs/LESSONS.md` from a template | threads, through gated PRs | every session, right after `add_repo` |
| **State** (volatile, days) | goal and deadline, live projects, pending on yskills, open threads, the project's products | the project's `MEMORY.md` only, in the shape of `operator/templates/project-memory.md` (five fixed sections, under 3 KB, no fact files) | the coordinator at milestones; threads only their own thread line | automatically, every start |
| **Boot text** (pasted once) | how a session gets to layer 1 and 2 | Project settings > Project instructions, generated by `node scripts/project-instructions.mjs <project>` from the template plus `projects/<name>.json`; under 15 lines; never a rule | yskills pastes, once | every session of that project |
| **History** (reports) | research, audits, handoffs, screenshots | `/mnt/project-files/<project>/` and `docs/archive/` in the repo; never cited as a rule (`docs/MAP.md`, Keeping it clean) | threads | only when named in a brief |

The thread board is not a store: the coordinator reads it at every start and reconciles it with
the `Threads` section of `MEMORY.md` (the board wins; memory is corrected in the same turn).

### What every session does at start

| Surface | Reads first | Then |
|---|---|---|
| Coordinator (project chat) | `MEMORY.md` (state), `list_thread_sessions` (board) | `add_repo` claude-setup, `CLAUDE.md`, `docs/MAP.md` Start here, `operator/roles/project-manager.md` Session start; reconciles board and state; posts nothing unless something is wrong |
| Thread | its brief, `MEMORY.md` | `add_repo` claude-setup, `CLAUDE.md`, `docs/MAP.md` Start here, its role file; for a product: that repo's `CLAUDE.md` and `docs/LESSONS.md` |
| Claude Code on the laptop | `~/.claude/CLAUDE.md` (installed copy) | the project's `CLAUDE.md`; auto-memory stays a scratchpad, emptied by the memory check |
| A new claude.ai project | the generated boot text | as a coordinator above; its first session runs the one-time sweep (below) |
| A plain chat (no project) | yskills' user preferences (already: add claude-setup, read `CLAUDE.md`) | `docs/MAP.md` Start here; the `operator` skill sizes the job and staffs the team; no memory, so state comes from the repo and the product repo only |

### Where a lesson goes (the one decision tree)

1. A mechanical pattern (a banned call, a file rule, a number): a check in `scripts/` or CI, not text.
2. True for every project: the home named in `docs/MAP.md` (One home per rule); no home yet: a new row there.
3. True for one product only: `<product repo>/docs/LESSONS.md` (template `operator/templates/lessons.md`), dated, newest last.
4. State (what is open, who owes what): the `MEMORY.md` section it belongs to.
5. Everything else (how the day went, a dead end, a report): `/mnt/project-files/<project>/`, named from the PR or thread; nothing to do.

Every PR body answers `Lessons:` with a path or `none, because <why the next thread would not repeat it>`
(the bar from Every's ce-compound, already in `docs/WORKFLOW.md` Learning). CI fails a PR without the line.

### Memory check, two speeds

- **Every coordinator start, cheap:** `MEMORY.md` has only the five sections and no line that is a rule
  ("Models", "merge", "never", "always" without a pointer); a rule found there becomes a `loop:setup` issue.
- **Monthly, or on "memory check":** every fact file and auto-memory note is moved into its home or deleted
  (`docs/WORKFLOW.md`, Learning), the raw copy archived first.

### Other projects (Company XY, Social Media Manager, game projects)

yskills does one thing per project, once: paste the generated boot text. Everything else is automatic:
the boot text tells every session that shared lessons go to claude-setup and product lessons to
`<product repo>/docs/LESSONS.md`, and its first session after the paste runs the one-time sweep: read that
project's `MEMORY.md` and fact files, move each lasting line into its home (one PR per repo), archive
the raw files under `docs/archive/<project>-memory-<date>/` in claude-setup, rewrite `MEMORY.md` from
the template, delete the fact files, report in three lines. The sweep is the monthly memory check run
once, so it needs no new mechanism.

## 5. Decisions taken (no card needed) and why

- State stays in `MEMORY.md`, not in a repo file: it changes daily, the coordinator has no git, and
  `main` is gated. The template makes it one shape; the cheap check keeps rules out of it.
- Reports stay in `/mnt/project-files/` and get a zip archive, not a move into git: 259 MB of images
  and renders would bloat every clone; the 68 KB of text is zipped and the lasting lines move.
- The boot text stays a pointer, never a rule: a rule there is a second source by construction.
- Auto-memory on the laptop stays on as a scratchpad (decided 10-18, `docs/WORKFLOW.md` Learning); the
  memory check empties it.

## 6. Risks and what is not checked

- Deleting a fact file in `/tmp/claude/memory/team/silo/` is expected to delete it in the memory
  service (the memory instructions say to delete wrong memories); PR 4 verifies after a fresh
  thread start that the files are gone and `MEMORY.md` is the new one, before it reports Done.
- This thread cannot read other projects' memory; their sweep runs in their own first session after
  the paste (§2). The list of projects to paste into comes from yskills' project list, which only he sees.
- The claude.ai limit on project-instructions length is not published; the generated text stays
  under 15 lines (the current pasted text is about 40 and loads).
- Research behind §2 (Anthropic memory and CLAUDE.md guidance, public setups): `docs/research/2026-10-25-memory-and-source-of-truth.md`.
